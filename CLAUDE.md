# PushFPS — notes for Claude and other agents

PushFPS is built on Veyra (https://github.com/Likely7/Veyra-NRVideo, GPL-3.0) and focused on console
frame generation from a capture card. It started as a fork; since 2026-11-17 the repository stands on its
own (not a GitHub fork). Owner: DosukaSOL. Repository: https://github.com/DosukaSOL/PushFPS.

These rules take precedence over `AGENTS.md`. `AGENTS.md` is Veyra upstream's own work log (Chinese,
with paths on the upstream developer's machine); read it for history and engineering contracts, but its
paths, task lists and push/release rules are not ours. Do not edit it: it changes upstream almost daily
and edits would conflict on every merge.

## Rules

1. **Keep upstream mergeable.** Internal identifiers keep Veyra's names: namespaces (`veyra::`), CMake
   targets, the `qml/Veyra` QML module, window classes, data folders, env vars (`VEYRA_*`). Only what a
   user sees says PushFPS. That includes the files in the log folder (the owner's decision, 20 November
   2026): since 4.0 they are `pushfps-qml.log` (`.old.log`), `pushfps-last-failure.txt`,
   `pushfps-last-session.txt`, `pushfps-crash-*.dmp` and `pushfps-hang-*.dmp`; `apps/veyra-qml/main.cpp`
   takes the `veyra-*` files of an older version over once at start. Name any new file a user can find
   after PushFPS, never after Veyra. Product name and links live in `include/veyra/Brand.h`; use it instead of
   writing the name or URLs again.
   The owner's instruction of 20 November 2026, for everything taken from upstream: "make sure their name isn't
   branded into every bit of code. Wherever you can without breaking the open source licence, make sure it says
   PushFPS instead of Veyra." So whatever a user, Windows or another program can see or find carries PushFPS's
   name the moment it is merged: device names, COM classes and registry keys, named kernel objects, installed
   files and folders, every text. Licence notices, copyright lines and SPDX headers stay (the GPL requires them).
   The identifiers inside the source keep upstream's names, as above; he was told so and why.
2. **Translations are keyed by the Simplified Chinese source string.** Every user-visible string is
   written in Chinese in `qsTr(...)` / `tr(...)` and translated in `i18n/catalog.json` (zh-TW, en, ja, ko by hand). For nl, de, es, fr, it, pt-BR, tr, ar,
   pl, ru the short interface labels are hand-written in `scripts/i18n/hand/<lang>.txt` (line order of
   `hand/en.txt`; fix a word there, never in the catalog) and longer texts are machine-translated by the
   `translate` workflow (`machine_translate.py`, which corrects wrong-sense words and keeps English for half-translated output, `merge_translations.py`, then
   `apply_hand_translations.py`), which pushes the result to the `i18n-mt` branch.
   After changing or adding a string run `python3 -B scripts/i18n/extract.py`, fill the new entries, then
   `python3 -B scripts/i18n/extract.py --check` must report 0 missing and 0 placeholder problems.
3. **QML is loaded from disk next to the exe** (`qml/Veyra`), so new QML files need a line in
   `qml/Veyra/qmldir` but no CMake change. Run the QML lint workflow (`.github/workflows/checks.yml`) on
   every QML change; there is no other QML check without a Windows build.
4. **Never commit** SDKs, NVIDIA/AMD/Intel runtimes or models, build output, or user data (exception:
   MIT-licensed shader source such as `third_party/nis`, recorded in `THIRD_PARTY_NOTICES.md`)
   (`.gitignore` covers `third_party_local/`, `runtime_local/`, `out/`, `build/`).
5. **License.** Everything stays GPL-3.0 (the Chiaki remote-play part also AGPL-3.0). Veyra is credited for
   what it is: the foundation of the engine. "Built on Veyra" by Likely7 stays in the app's About page, the
   README and the store copy, and the licence notices in the source files stay (the GPL requires them).
   On 20 November 2026 the owner said nothing else should credit it; on 21 November (after seeing that
   Veyra 2.2.0 took PushFPS features with credit in its source only, and asking its developer for a visible
   one) he said: "make sure we DO properly credit him in the way we're supposed to in our new release", and
   then: "Dont credit him obnoxiously everywhere... Keep it as subtle as possible while staying true to what
   i stand for." So: **a release that takes features from a Veyra release says so once**, in one short
   paragraph of its release notes that names the release and what came from it (4.1's "Built on Veyra
   2.2.0"), and the credits of the README and the website name the same in one sentence. No tag on every
   feature, nothing in posts beyond one line, and a fix written as PushFPS's own code after reading upstream
   is covered by that paragraph's "and a number of fixes". No sponsor links (removed in 3.1.3). Copy code from other projects only with a compatible license
   and record it in `THIRD_PARTY_NOTICES.md`. `NOTICE.md` holds the GPL-3.0 modification notice, the
   section 7 additional permission for PushFPS's own code (linking with the NVIDIA/AMD/Intel SDKs) and the
   NVIDIA SDK attribution (also in the About page, required by the NVIDIA RTX SDKs License). By default the
   installer never installs NVIDIA files that are not NVIDIA-signed originals, nor NVIDIA's model runtimes on
   AMD installs; they stay available as opt-in "experimental extras" (`-ExperimentalExtras Yes` or the
   installer's question) so no feature is lost (`packaging/Install-PushFPS.ps1`; CI checks both paths). Marketing describes features, not NVIDIA
   marks: no "DLSS" in headlines, no NVIDIA logos, never imply endorsement.
6. **Be honest about verification.** Say what was built, run and tested, and on which hardware. A change
   that only passed static checks is "unverified on Windows". That is for the engineering record (this
   file, `docs/PUSHFLOW*.md`, `docs/BENCHMARKING.md`, commit messages) and for what the owner is told.
   **What users read is different (the owner's instruction, 21 November 2026: "Whenever we have no hardware
   validation yet, just dont mention it at all. Only mention it when we do", and "Don't say it has
   either")**: release notes and the release page, the README, the website, the setup guide, the roadmap's
   "done" sections, posts, and texts in the app never say that something was not tested, not measured or
   not seen on real hardware, and never say or suggest that it was when it was not. No "what was tested"
   section, no "unverified", no "not tested yet" row. Hardware validation is named only where it exists
   (the tested graphics cards, a capture card tested or reported working). A limit a user has to know to
   use a feature is still said, as a limit and without the testing story ("full size is about four times
   the work").

## Building and releasing

- **A release is the owner's call.** (And so is a test build: on 22 November 2026 a test build started on
  the work branch for two more screenshots, announced to him, was answered with "Don't make it a test build
  i didnt ask for that" and cancelled. Start one only when he asks for one; what is needed to see can
  usually be photographed with `qml_from` over the last release's package.) Never push a tag or dispatch a release build before he says it is
  time, and while changes for a release are being collected start no build he has not been told about
  (20 November 2026: he stopped a test build started while 4.0 was being collected; later that day he said
  to build and publish 4.0 once everything was checked, and test builds on the work branch were announced
  to him first). Collect on a branch. Test builds there (`gh workflow run build-windows.yml --ref <branch>`)
  publish nothing, take an hour, and are the only place the Windows code is compiled: read every uncompiled
  change once more before starting one. `build-windows` also starts by itself on every push to `main` that
  touches code, so a merge to `main` before the release is called has `[skip ci]` in the last commit of the
  push. The release is then dispatched explicitly (`-f release_tag=vX.Y.Z` on `main`), checked
  (`gh api repos/DosukaSOL/PushFPS/releases/latest`: not a draft, not a pre-release, the signature line,
  every asset), and `build-portable.yml` dispatched with the same tag. What a change was checked by is said
  plainly: read, run without a build (`extract.py --check`, `protected_features.py`, the unit tests that
  build with g++), run in CI on the software renderer, or run on a real card.
- **Names the Windows headers take away.** `small`, `far` and `near` are macros there: never a variable of
  that name in C++ a Windows file can include, pure headers included (4.0's still rule had `near` in its
  header; g++ compiled it, MSVC would not have). The check without a build: a file that defines the three as
  macros, includes the new headers and is compiled with `g++ -std=c++20 -fsyntax-only -Iinclude`. Headers
  that need `d3d12.h` build locally against a stub folder with empty Windows headers.

- After any QML change, `tests/qml/quick` runs in CI (`tst_push_*.qml` in their own step, then the whole suite: a failure in either
  fails the build; the fixture all of them share is one QML object in `tests/qml/QuickSmokeTests.cpp`, and a
  property declared twice there stops every test at start, as does a `signal xChanged()` beside `property x`,
  which already has that signal: `python3 -B scripts/checks/qml_fixture.py` finds both in a second and runs in
  the checks workflow; the `qml-tests-fast` workflow runs the `tst_push_*.qml` tests on Linux in a few minutes
  on every push to a work branch that touches `qml/` or `tests/qml/`, never on `main`: an early word, the
  Windows build is the one that counts) and the install test opens every main page and fails on `[ERROR] [qml]`. Two things a dialog's

## Syncing with Veyra

```
git remote add upstream https://github.com/Likely7/Veyra-NRVideo.git   # once
git fetch upstream main
git merge upstream/main
```

Expected conflicts: `README.md`, `README_CN.md`, `README_EN.md` (keep ours), `i18n/catalog.json` (keep ours,
save theirs with `git show :3:i18n/catalog.json`, run `extract.py`, fill the new entries from theirs, then
`--check`), and any file listed in the table above.

After the conflicts, before anything is built: `python3 -B scripts/checks/merge_duplicates.py <merge base>
<upstream ref>` (upstream copies PushFPS features, and git puts the copy beside the original without a word),
a search for upstream's product name in everything a user or Windows can see (rule 1), and a look at every
new feature for what it opens, downloads, runs or sends: new things start off.
